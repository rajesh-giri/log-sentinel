# Log Sentinel

A full-stack SOC (Security Operations Center) log analysis tool. Upload an Nginx/Apache-style
access log, get a parsed timeline of events, and see anomalies automatically flagged with
plain-English explanations and confidence scores.

Built as a take-home exercise. Focused on functionality over production-readiness, per the
exercise's own ground rules.

![stack](https://img.shields.io/badge/stack-Next.js%20%2B%20TypeScript%20%2B%20Postgres-22d3ee)

## What it does

1. **Log in** with a seeded account (basic session-cookie auth).
2. **Upload** a `.log`/`.txt` access log file (drag & drop or click to browse), up to 5MB.
3. The backend **parses** every line into structured events (timestamp, IP, method, path, status,
   bytes, user agent), stores them in Postgres, and runs **two layers of anomaly detection**:
   - Deterministic statistical/rule-based detectors (always run, no external dependencies).
   - An optional LLM pass that looks for higher-order patterns and writes natural-language
     explanations (only runs if `GEMINI_API_KEY` or `OPENAI_API_KEY` is set — see
     [AI Usage](#ai-usage) below).
4. The **results page** shows a chronological incident timeline strip, a traffic volume chart, a
   SOC-analyst-style narrative summary, a list of anomalies (with severity + confidence score), and
   a searchable/filterable events table that highlights exactly which rows triggered each anomaly.

## Quick start (Docker)

The fastest way to run everything (app + Postgres) locally:

```bash
docker compose up --build
```

Then open [http://localhost:3000](http://localhost:3000) and log in with:

- **Username:** `analyst`
- **Password:** `password123`

(These are seeded automatically on container startup — see `SEED_USERNAME`/`SEED_PASSWORD` in
`docker-compose.yml` if you want to change them.)

To use the LLM-assisted anomaly detection and narrative summaries, set `GEMINI_API_KEY` or
`OPENAI_API_KEY` in your shell before running compose (both are passed through automatically; if
both are set, Gemini takes priority):

```bash
GEMINI_API_KEY=... docker compose up --build
# or
OPENAI_API_KEY=sk-... docker compose up --build
```

Without an API key, the app still works fully — it just relies on the statistical detectors and a
template-based summary instead of an LLM-generated one.

## Quick start (local, without Docker)

Requires Node.js 20+ and a running Postgres instance.

```bash
npm install

# Point DATABASE_URL at your Postgres instance (see .env.example)
cp .env.example .env

# Create tables and seed the demo user
npx prisma migrate deploy
npm run db:seed

npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

## Sample log files

Three synthetic log files are included in [`sample-logs/`](./sample-logs) (generated by
[`scripts/generate-sample-logs.ts`](./scripts/generate-sample-logs.ts), with a seeded PRNG so
regenerating them is reproducible rather than occasionally shifting a borderline detector result):

- **`normal-traffic.log`** — ordinary human browsing sessions (~60 short sessions, 3-10 page
  views each) plus two deliberately-included **legitimate automated clients**: a `curl`-based
  monitoring/health-check poller and a real-Googlebot-UA crawler walking every page once. The
  detectors currently flag both of those as anomalies — see "Known limitations" below; this file
  is a smoke test that ordinary browsing stays quiet, not a "zero false positives" claim about the
  detectors as a whole.
- **`with-anomalies.log`** — the same kind of baseline browsing traffic (no poller/crawler mixed
  in here), plus three injected attack patterns from distinct IPs:
  - A request-rate burst (180 requests in ~45s from one IP using `curl`).
  - Endpoint/directory scanning (one IP hitting 20 sensitive paths like `/wp-admin`, `/.env`,
    `/.git/config`, SQLi-looking query strings, etc., mostly 404s) — this also trips the dedicated
    sensitive-path detector, independent of the scan's breadth.
  - An off-hours credential-stuffing pattern (repeated `401`s between 02:00-04:00 UTC from a
    `python-requests` client).
- **`llm-pattern.log`** — baseline browsing plus one IP performing a subtle "insider abuse" pattern
  (browses `/admin/dashboard` and `/admin/users`, then `DELETE`s two other users' accounts, then
  exports the customer list — 6 requests total, all `200`s, real Chrome UA, off-hours). Deliberately
  built to sit under every statistical detector's fixed threshold individually (too few requests
  for a rate spike, no errors, too few distinct paths for scanning, no sensitive-path substring
  match, no scripting-tool UA) — only the generic, low-confidence "off-hours activity" rule fires.
  This is the one fixture meant to exercise the **LLM pass**, not the statistical detectors: reading
  the method/path breakdown in aggregate (see `summarizeEvents`), a capable model correctly narrates
  it as a likely authorization bypass with active data deletion — see "AI Usage" below for what
  model tier that requires.


Regenerate them anytime with `npx tsx scripts/generate-sample-logs.ts`.

## Testing

```bash
npm test
```

Runs the statistical detectors against both fixtures in `sample-logs/` (`tests/detectors.test.ts`)
and asserts: ordinary human browsing sessions in the clean file produce zero anomalies (excluding
the two known-false-positive automated clients, which are asserted explicitly instead of hidden —
see below), the anomaly file produces the rate-spike/scan/off-hours/sensitive-path categories, and
the endpoint scan outranks a suspicious-user-agent finding by severity. It's a coarse smoke test
against two fixtures rather than exhaustive unit coverage of every detector branch, but it turns
"does it actually work?" into a command instead of a claim.

## AI usage

This section documents, as requested by the exercise, exactly how and where AI/LLMs are used.

**Where AI is used:**

1. **Secondary anomaly detection pass** (`src/lib/llm/anomaly-detector.ts`). After the statistical
   detectors run, an optional LLM pass is given a *bounded aggregate summary* of the log (overall
   stats + per-IP behavior for the most active IPs — never raw log lines) plus the anomalies
   already found, and is asked to identify additional suspicious patterns that are hard to encode
   as fixed thresholds — combinations of individually-weak signals (a rare path *combined with* an
   odd method *combined with* off-hours timing) or genuinely novel patterns that don't match any
   detector's fixed shape. It's explicitly told not to re-flag known-bad paths, since those are
   already caught deterministically (see below). It returns anomalies with its own `category`,
   `description`, `confidence`, and `severity` via a JSON-schema-constrained response, with
   `temperature: 0` for reproducibility.
2. **Narrative timeline summary** (`src/lib/llm/timeline-summary.ts`). Given the same aggregate
   summary plus the full list of detected anomalies (from both layers), the LLM writes a short,
   plain-English SOC briefing paragraph — the kind of thing a human analyst would jot at the top of
   an incident ticket. If no API key is configured, a deterministic template-based summary is used
   instead (see `buildFallbackSummary` in the same file), so the app is fully usable without AI.

**Where AI is deliberately *not* used:**

- **Log parsing** (`src/lib/parser/access-log.ts`) is a plain regex-based parser. Structured log
  formats don't benefit from an LLM in the loop — it would be slower, non-deterministic, and more
  expensive for a task regex already does exactly right.
- **The statistical detectors** (`src/lib/detectors/statistical.ts`) — rate-spike (a ratio-over-
  baseline threshold, with a z-score path for IPs that have enough of their own history to
  establish a real baseline), error-rate outliers, endpoint scanning, sensitive path/credential
  probing, off-hours activity, and suspicious user agents — are all deterministic. They're the
  detection layer that's always on, always explainable, and doesn't depend on an external API
  being available or affordable at upload time. Notably, requests to known-sensitive paths
  (`.env`, `.git/config`, cloud credential paths, admin panels, SQLi-shaped query strings) — the
  strongest single security signal this tool produces — are caught by a fixed rule, not the LLM,
  so that finding never disappears just because no API key is configured.

**Why a hybrid (statistical + LLM) approach:** pure statistical rules are fast, free, and fully
explainable, but they can only catch the specific shapes of anomaly they were written for. An LLM
pass, fed a compact summary rather than raw logs, adds a layer that can reason about combinations
of individually-weak signals and patterns that don't fit any fixed rule — while staying cheap
(summary size is independent of file size) and safe to skip entirely if no API key is present.
This does narrow what's uniquely the LLM's to find, on purpose: the highest-signal detection in
the tool shouldn't be the one that depends on an external API.

**User-controlled toggle:** the LLM pass adds real latency (tens of seconds against a live API,
observed ~40s vs. ~0.1s in local testing) for one AI-generated finding at most, on top of the
statistical detectors that already run in milliseconds — not something to pay silently on every
upload. The upload page has a "Run AI-assisted anomaly detection" checkbox (on by default); turning
it off before uploading skips both LLM calls (anomaly pass and narrative summary) server-side
entirely — it's not a display filter applied after the fact, the API route
(`src/app/api/uploads/route.ts`) never calls `runLlmDetector`/`generateTimelineSummary` when the
flag is off, and the narrative summary falls back to the same deterministic template used when no
API key is configured at all.

**Model:** defaults to `gpt-4o-mini` via the OpenAI API, or `gemini-3.5-flash` via the Gemini API if
`GEMINI_API_KEY` is set instead (`OPENAI_MODEL`/`GEMINI_MODEL` env vars to change either). The Gemini
default is deliberately not the cheaper "-lite" tier — see `sample-logs/llm-pattern.log` above:
testing showed `gemini-flash-lite-latest` consistently missed that subtle multi-signal pattern
(0/2 runs) while `gemini-3.5-flash` caught it reliably (2/2 runs). A model too weak for that
reasoning defeats the purpose of running an LLM pass at all, so the extra cost/latency over the
lite tier is a deliberate tradeoff, not an oversight. Both
providers are used through the same `openai` SDK — Gemini exposes an
[OpenAI-compatible endpoint](https://ai.google.dev/gemini-api/docs/openai), so switching providers
is just a different `baseURL`/API key rather than a second SDK integration (see
`src/lib/llm/client.ts`). General-purpose coding assistance (via Cursor) was also used throughout
to scaffold and implement this project.

## Anomaly detection details

Each anomaly includes a `category`, a plain-English `description`, a `confidence` score (0–1), a
`severity` (`LOW`/`MEDIUM`/`HIGH`/`CRITICAL`), and a `source` (`STATISTICAL` or `LLM`).

**Severity and confidence are deliberately two independent axes, not two views of the same
number:**

- **Severity** answers "how bad would this be if it's real?" It's a fixed property of the
  category/condition a detector matched (e.g. a hit on a known-sensitive path like `.env` or
  `.git` is always `CRITICAL`; a non-browser user agent alone is always `LOW`), not something
  derived from confidence.
- **Confidence** answers "how strong is the statistical signal?" It's an **ordinal ranking of
  signal strength within a detector** (a bigger z-score, a higher error ratio, more distinct
  paths hit → a higher number) — **not a calibrated probability of a true positive.** A confidence
  of 0.88 does not mean "88% likely to be a real attack"; it means "this is a stronger match for
  this detector's pattern than one scoring 0.60." Treat it as a ranking signal for triage order,
  not as a statistically validated likelihood.

Severity is set per-detector based on what the finding actually means, independent of how
confident the detector is in that particular instance:

| Detector | Signal (drives confidence) | Severity |
|---|---|---|
| Request rate spike | An IP's requests-per-minute in some 60s window is a z-score outlier vs. its own baseline; falls back to comparing against the file-wide average rate when there's too little of that IP's own traffic to establish a baseline. | `MEDIUM` alone (a spike has plausible benign explanations — health checks, polling clients); escalated to `HIGH` only if the same IP is *also* independently flagged by another detector at `MEDIUM` severity or above. Deliberately excludes corroboration from `LOW`-severity findings (off-hours activity, suspicious user agent) — those are weak signals by design, and letting two weak signals escalate each other into `HIGH` would just relocate the "severity derived from weak signals" problem this table's whole design is meant to avoid. |
| High error rate | An IP where ≥50% of requests return 4xx/5xx. | `HIGH` when the errors are dominated (≥60%) by `401`/`403` — a credential-stuffing/brute-force signature; `MEDIUM` otherwise (reads more like generic scanning noise, already captured more specifically by Endpoint scanning). |
| Endpoint scanning | An IP hitting a large number of distinct paths relative to its request count (enumeration signature) — a breadth/volume signal, independent of whether the paths themselves are sensitive. | `HIGH`. |
| Sensitive path access | Any request (regardless of volume) to a known-sensitive path or SQLi-shaped query string — `.env`, `.git/config`, `.aws/credentials`, `wp-admin`, `phpmyadmin`, `actuator/*` (excluding `actuator/health`), `' OR '1'='1`, `UNION SELECT`, etc. | Always `CRITICAL` — a single targeted probe of secrets/credentials/admin surfaces doesn't need corroborating volume to be worth flagging. **Caveat, volunteered rather than hidden:** several patterns match on substring, not exact known-bad paths (`credentials`, `cgi-bin`), so on real production traffic some of these are false-positive-prone — e.g. `/api/v1/credentials/rotate` is a plausible legitimate endpoint, and `/cgi-bin/` is a normal (if dated) path on plenty of hosts. Tuned to catch the injected sample-log patterns cleanly, not validated against real-world traffic; see "Known limitations". |
| Off-hours activity | An IP concentrating most of its traffic between 01:00–05:00 UTC. | `LOW` — timing alone is weak, corroborating evidence; plenty of legitimate automated/global traffic runs off-hours. |
| Suspicious user agent | Requests from known scripting/scanning tools (`curl`, `python-requests`, `sqlmap`, `nikto`, etc.) or missing UA strings. | `LOW` — a non-browser UA alone is weak, corroborating evidence; legitimate bots and API clients use these same strings. |
| (LLM) Pattern-based | Higher-order/semantic patterns from the LLM pass — see [AI Usage](#ai-usage). | Set by the model per-instance; not derived from a fixed rule like the statistical detectors above. |

**Incidents, not raw anomaly cards:** a single injected attack often trips several detectors for
the same IP (a scan also reads as a burst of errors and a suspicious user agent). The results UI
groups anomalies by IP into one incident card per actor (`src/lib/group-incidents.ts`), listing
each contributing signal underneath rather than showing eight overlapping cards that all point at
the same source — closer to how a SOC analyst actually triages ("what is this IP doing"), and
easier to explain on review. Anomalies without an IP (which the LLM pass can produce) stay as
their own single-signal incident. Clicking an incident card filters the events table down to just
the events behind it and highlights the corresponding entries on the incident timeline strip;
flagged rows are also highlighted (red dot) when browsing the full table.

Two granularity/accuracy seams worth being upfront about rather than leaving for someone else to
notice:

- **The incident panel and incident timeline disagree on granularity, on purpose.** The panel
  groups by IP (one card per actor); the timeline strip lists per-anomaly, since the individual
  signals for one IP happen at different times and collapsing them into a single point would lose
  that. Defensible, but it means the two views can show different counts for what looks like "the
  same" incident (e.g. 3 incident cards vs. 10 timeline entries) — worth having that answer ready
  rather than looking like an inconsistency.
- **LLM findings over-attribute events.** `linkAnomaliesToEvents` (`src/lib/link-anomalies.ts`)
  resolves an LLM-flagged IP to *every* `LogEvent` row for that IP, because the LLM only ever sees
  aggregate per-IP stats and never returns line numbers to be more specific with. That's better
  than the alternative (an LLM finding that can't highlight anything at all), but it means "N
  related events" and the incident's time window reflect that IP's *entire* session in the file,
  not specifically the events that made the pattern look suspicious. A tighter fix would require
  either sending the LLM more granular data (defeats the bounded-summary design) or having it
  return which of the summary's `topPaths`/time buckets it's referring to and intersecting on
  that — not currently implemented.

## Architecture

- **Frontend:** Next.js 16 (App Router) + TypeScript + Tailwind CSS. Dashboard/upload page and a
  results page (chart via Recharts, table, anomaly panel) — see `src/app` and `src/components`.
- **Backend:** Next.js Route Handlers (`src/app/api/**`) — a monolith rather than a separate
  service, since it satisfies "a Node.js backend" while cutting significant setup/deploy overhead
  for a time-boxed exercise. Auth is a signed JWT session cookie (`jose`), verified in
  `src/proxy.ts` (Next.js's request-interception layer, formerly "middleware") on every
  non-public route.
- **Database:** PostgreSQL via Prisma (`prisma/schema.prisma`). Four models: `User`, `Upload`,
  `LogEvent`, `Anomaly` (anomalies reference the specific events that triggered them via an
  implicit many-to-many).
- **Parsing → detection pipeline:** `POST /api/uploads` does everything synchronously per request
  (parse → statistical detectors → summarize → LLM pass → persist). That's a reasonable choice at
  the file sizes this exercise targets; for large files in a production system this would move to
  a background job with a status-polling UI instead (the `Upload.status` field —
  `PROCESSING`/`COMPLETE`/`FAILED` — already anticipates that).
- **Upload limits:** files are capped at 5MB. Every event is still parsed, stored, and fed to the
  anomaly detectors regardless of file size — the cap exists to keep the synchronous request loop
  above bounded, not to limit detection coverage. The results page itself only renders the first
  5,000 events in the table/chart (with a banner noting the truncation) since serializing an
  unbounded event list into a client component doesn't scale; anomaly cards and the SOC briefing
  reflect the full file regardless.

## Known limitations / things to call out

Being upfront about scope, since "only submit code you're comfortable explaining" was one of the
ground rules:

- Upload processing is synchronous — a very large file would block the request. Fine for the
  demo/exercise scale; the `Upload.status` field is designed to make moving this to an async job
  straightforward later.
- The parser targets one log format (Nginx/Apache "combined"). It's built as a normalized
  `ParsedLogEvent` shape specifically so other formats could plug in without touching the rest of
  the pipeline.
- The LLM anomaly pass sees aggregate statistics, not raw log lines, by design (cost/latency stay
  flat with file size) — it can miss anomalies that only show up in a specific event body's
  content rather than in aggregate behavior.
- No rate limiting or CSRF protection on the API — reasonable for a local/demo tool, not something
  I'd ship as-is to production.
- **Two known, deliberately-surfaced false positives**, visible today in `sample-logs/normal-
  traffic.log` (see `tests/detectors.test.ts`, which asserts them explicitly rather than only
  asserting "zero anomalies" and hoping nothing legitimate-but-automated is in the fixture):
  - A constant-rate `curl` health-check/monitoring poller trips "Suspicious user agent" — `curl` is
    always treated as non-browser, but it's also one of the most common legitimate uses in
    production (uptime checks, load balancer probes, cron jobs).
  - A real-Googlebot-UA crawler walking every page once trips "Endpoint scanning" — that detector
    is UA-blind by design (breadth of paths hit, not who's hitting them), so a legitimate crawl
    with enough distinct pages looks identical to enumeration.
  - Neither is a bug in the strict sense — both detectors are doing exactly what they're specified
    to do — but they're real false positives a SOC analyst would have to triage, and I haven't
    validated the detectors against real production traffic beyond these two synthetic cases.
    Fixing them properly (an allowlist of known monitoring IPs/UAs, or requiring scanning breadth
    *and* a non-crawler UA before flagging) is a reasonable next step, not something I'd claim is
    already handled.
- **Sensitive-path detector is substring-matched, not exact-path-matched**, so it's also
  false-positive-prone on real traffic beyond the two cases above — see the caveat in the detector
  table. `actuator/health` is excluded explicitly since it's the single most common legitimate hit,
  but `credentials` and `cgi-bin` still match broadly (e.g. `/api/v1/credentials/rotate`,
  `/cgi-bin/anything`) and would flag CRITICAL on a real production log. Always-`CRITICAL`-with-no-
  volume-floor was a deliberate choice (a single probe of `.env`/`wp-admin`/etc. is worth flagging
  without waiting for repetition), but it means this detector has the least margin for a bad
  pattern match — worth an allowlist of known-benign full paths before relying on this against real
  traffic.
